# Unit 1: Justification & Reflection

**Task 1.4: your modelling justification and your reflection**

>1. Modelling justification, 400 to 600 words. Cover your key design decisions: your choice of primary keys, your ON DELETE behaviors, and which rules you chose to enforce in the schema rather than leaving to the application.

   Attributes are chosen as a primary key if they need to be unique throughout the table. For example, passenger_id must be a unique value because each passenger has a different ID number — one person can only have one ID number, and it can never be duplicated. Only one booking_id can be created at a time; if another booking is made, it will be assigned a different ID number. Each airline route has its own flight_id, and unless the route is canceled, it will remain unchanged. If the route gets canceled or temporarily paused, the data will still remain, but the status will simply be turned to inactive or canceled.

    On delete behavior appears mostly on the passenger's side. If a passenger deletes account information, such as phone or email, those fields will return NULL. However, if it is a primary key — such as when the account itself is removed — the NULL will remain in the table, since it is linked to other historical records for that passenger, like historic booking data, which we do not want to remove. This is because if the removed passenger later re-registers an account, we can link it back to their original account information and data. For most attributes in this table, if there is no data entered, it will return as NULL so other fields data in the same table or are related to it (if it is a FK) can still remain.

    I enforce domain constraints on the FK attributes, as well as on some fields that require non-duplication and entry limitations from the user. For example, passenger_email, passenger_phone must have a formatting constrain to protect the data from receiving trash or taking up too many space. Each design is considered for their needs, constrains, and possible record updates on their FK or related fields across.


> 2. Reflection, 150 to 250 words. Your ERD encodes decisions the requirements left open. Name one decision you made that a different designer could reasonably, have made differently, and defend your choice in terms of the read and write patterns the platform will face.

    I designed my ERD based on the 5 schemas provided and each of their role provided in the assignment. If someone else were to create it, they might combine some of them together. Flights and Airport are very similar and could possibly be combined into one schema instead of two. This would consolidate the tables and also avoid many duplicate fields between the two. Another possibility is creating more tables and grouping them once there is more data in the company. In terms of future scalability problems, there could be some difficulty as the data scales. I also need to see if NULL is returned frequently in some fields; if so, those will need to be reconsidered as required. However, for starting a new airline, this is sufficient to begin with. I also have not considered the data-passing timing. That would changes the design of the tables.
